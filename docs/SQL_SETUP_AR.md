# إعداد Supabase — خطوات دقيقة

## ترتيب التنفيذ

يمكنك تنفيذ `supabase/INSTALL_ALL.sql` مرة واحدة؛ وهو يضم الملفات الثلاثة التالية بالترتيب. أو نفّذ الملفات الثلاثة منفصلة، ولا تجمع بين الطريقتين.

1. `0001_clean_install.sql`: ينشئ الجداول الأساسية والأنواع والفهارس وRLS والدوال الأولية.
2. `0002_approvals_rehab_storage.sql`: يهيّئ Storage الخاص بسياسات المؤسسة، ودالة مالك المنصة، وحماية أرشفة السنة.
3. `0003_integrity_and_lifecycle.sql`: يفعّل إنشاء الحسابات والموافقات الهرمية، قيود العلاقات متعددة المؤسسات/السنوات، ملفات المنشآت، مدد الاختبارات، حماية الجلسات، تنبيهات التأهيل، واستيراد/تصحيح النتائج الآمن.
4. أنشئ أول Auth user دون institution slug عندما لا توجد مؤسسة.
5. عدّل ونفّذ `BOOTSTRAP_AR.sql`.

## متغيرات Bootstrap

استبدل القيم التالية قبل التنفيذ:

- `OWNER_EMAIL_HERE`: البريد المطابق لحساب Authentication.
- `OWNER_FULL_NAME_HERE`: الاسم المعروض للمالك.
- `INSTITUTION_NAME_HERE`: اسم المؤسسة الأولى.
- `INSTITUTION_SLUG_HERE`: رمز فريد صغير الحروف دون مسافات.
- `SCHOOL_YEAR_NAME_HERE`: تسمية السنة الدراسية.
- `SCHOOL_YEAR_START_DATE_HERE`: تاريخ البداية بصيغة YYYY-MM-DD.

نفّذ Bootstrap مرة واحدة. لا تشغّل ملف bootstrap بنصوص placeholders.

## حسابات المؤسسة

- المالك ينشئ المؤسسة ويعتمد حساب مدير المؤسسة.
- مدير المؤسسة يشارك slug مع الأعضاء، ثم يعتمد المدربين وبقية الإدارة.
- لا توجد صلاحية لتغيير الدور من واجهة المستخدم أو profile update مباشر.
- إذا كان الحساب معلّقًا، تحقق من أن slug صحيح وأن مدير المؤسسة اعتمده.

## سياسة البيانات

- لا يحتوي أي migration على DROP TABLE أو TRUNCATE أو DELETE FROM.
- المخطط نظيف وليس migration آليًا لقاعدة قديمة. إذا كانت لديك جداول قائمة، لا تشغّل 0001 عليها؛ أوقف التنفيذ واطلب مراجعة schema منفصلة.
- لا توجد Audit Log.
- `test_results` لا تقبل insert/update/delete مباشرًا من authenticated؛ تتم الإضافة والتصحيح عبر RPC تتحقق من BARÈME في قاعدة البيانات.
- إصدارات BARÈME غير قابلة للتعديل أو الحذف بعد إنشائها.
- لا تحذف حساب المالك أو بيانات Auth من SQL bootstrap.
